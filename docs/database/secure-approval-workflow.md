# Secure approval workflow

Applied to the connected Charvi Supabase project on 2026-11-23.

- Each approval request must carry a SHA-256 digest of the canonical action payload.
- An approval nonce is generated by Postgres.
- Approval requests start pending; request scope and payload are immutable.
- A pending request can transition once to approved, rejected or cancelled.
- Human approvals/rejections require a Supabase Auth user ID and decision timestamp.
- Decisions after expiry are rejected by the database trigger.
- Request and decision events are appended automatically to `approval_decision_events`.
- The audit table has RLS enabled, is readable only by the backend service role, and has no direct insert/update/delete grants for app/backend roles.
- The trigger function lives in the unexposed `private` schema and has no direct execute grants.

The backend still needs to authenticate the owner, fetch the persisted approval by ID, verify its status/hash/nonce/expiry, and then pass the verified binding to the action gateway. The current API does not yet create or decide approval requests.
